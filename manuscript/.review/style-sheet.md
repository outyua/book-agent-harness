# 体例共享账本（style sheet）

> 立于 2026-08-20。随第 6 章第 1 轮改稿创建（第 1 章当时尚未改）。与 [编辑方针](editorial-charter.md) 冲突时以方针为准。本表只记录执行时做出的具体定名与写法，不另立新规。后轮追加，不得无故改已有决定；与作者裁决冲突的条目覆盖并写明日期，后轮不得把已覆盖的旧条再执行回去。
>
> 2026-08-20 作者裁决：源码用来讲课，不是核验。覆盖 §4「三层引用」原「叙述句必须带注号」和「本章注：定位符」，以及 §6 原「定位符注可带 `[06-01 基准]`」、§11 原「细节进注」。

## 1. 部扉页

部扉页用三个自然段分别说明本部分覆盖的运行阶段、读者能完成的具体任务和章节依赖。信息固定，标签和句式不固定；禁止六个部分重复使用「这一部分管哪一段 / 读完你能做什么 / 章之间的依赖」三个加粗标签。部扉页无五段、无基准块、无本章注、无过期节。`verify-citations.sh` 体例完整性检查不扫 `part*.md`。

## 2. 章结构

- 段标题按内容拟定。第 4 段显示名「反面证据与失败模式」，第 5 段「可以直接采用的最小实现」。
- `## 本章注` 可无。有则插在第 5 段之后、`## N.6 版本与复核` 之前，不占五段序号。不要空节。第 1 章 2026-08-20 起无本章注。
- 章首禁止「读完这一章，你能……」。
- `####` 不用。

## 3. 历史引用

已从工作区删除的文件写成 `` `<仓库>@<提交>/<路径>` ``，按 `git cat-file -e <提交>:<路径>` 校验，不校验工作区路径。

## 4. 三层引用

> 本条已被 2026-08-20 作者裁决覆盖。源码用来讲课，不是核验。

| 位置 | 留什么 |
|---|---|
| 叙述句 | 项目名、机制、数字、判断、不成立的条件；短名；证据级别几个字。默认不带定位符注号。代码已在页上或表单元格已有路径，叙述句不再叠 `[^章-序号]`。会改变读法的几个字（厂商自述、未复现、通用 agent、本书测量、本书推算、论文实测、尚未通过同行评审）跟数字走，写在叙述句或后一句 |
| 对照表单元格、代码题注、§N.5.4 验收清单 | `file:line` 原样保留。这是讲课用具（这段代码在哪、对照地图），不是核验作业。表下禁止「口径见注」。不要专开「证据级别」列，用法见表后一句人话 |
| 本章注 | 可薄，可无。只收：（a）会改变用法且正文一句塞不下的限定；（b）短名解不到后记 C 的书目补遗。不 1:1 回填 `file:line`。测量方法、grep 口径、普查判定方法、推算链进「版本与复核」 |
| 基准块 | commit、日期、外部规格、测量命令、推算链；不吩咐正文去标 `[核]` |

同一出处一章一条注，后文复用。多数出处根本不建注。一条注只干一件事。

注号写法：`[^章-序号]`，章内从 1 连续。仅当出处身份会改变读法、且这句人话塞不进叙述句时才标。`verify-citations.sh` 扫对照表、代码题注、验收清单里的路径，不要为喂脚本把路径回填进本章注。

## 7. 证据级别（正文最多几个字）

`厂商自述` / `论文实测` / `本书测量` / `本书推算` / `本书推断`

A 级靠对照表或代码题注里的 `file:line` 显现，叙述句不写「源码实证」，也不叠定位符注号。

## 8. 数字、价格、倍率

- 价格不写 `$0.30`（构建链 Temml 会把 `$` 当公式）。写 `0.30 美元` 或 `0.30 美元 vs 3.00 美元 / 百万 token`。
- 倍率写 `1.25 倍`、`0.1 倍`、`2 倍`。
- token 比写 `100:1`。

## 9. 图与表

- 图题：`![图 {章}-{序号}：{描述}](path)`，冒号，置于图（即图片语法）本身；正文「见图 N-M」；图后保留「图 N-M 的结论用文字复述：」。
- 表题：`**表 {章}-{序号}：{描述}**`，置于表上方；正文「见表 N-M」。
- 第 6 章已编号：表 6-1 时间戳如何避免破坏前缀；表 6-2 缓存还热时各家如何推迟改上下文；表 6-3 可观测性四阶。
- 第 1 章已编号：表 1-1 四项目循环占比；表 1-2 三组只改 harness 的实验（无「证据级别」列，用法见表后一句人话）；表 1-3 四项目层次分布；表 1-4 确定性执行与模型推理；表 1-5 四象限例子；表 1-6 AHE 组件消融；表 1-7 演化 agent 的预测力；表 1-8 建造顺序；表 1-9 四象限盘点。
- 基准块表、保鲜期表不编号（版本与复核模板的一部分）。
- 表下禁止「口径见注」及其等价口吻（「详见注」「可核」）。

## 10. 代码题注

代码块后一行引用块，反引号包路径与行号。有省略时在题注写明。英文注释不翻译。

## 11. 诚实限定应放在哪里

厂商自述、推算不是实测、通用 agent 不是 coding agent、回看窗口是约数、fork 可能是继承、尚未通过同行评审、本书测量 / 本书推算 / 未复现：判断留正文或后一句。禁止为读感删掉，禁止藏进注再请人点开。测量方法、grep 口径、普查判定方法、推算链进「版本与复核」。正文一句塞不下的长限定才进本章注。表下禁止「口径见注」。（2026-08-20 覆盖原「细节进注」。）

## 12. 准确措辞与完整句子

> 2026-08-20 作者裁决：正文不使用省略实际含义的短词，也不通过极简句式要求读者自行补全动作、对象或条件。

- 不使用「判据」。确实指 criterion 时写「判断标准」；指执行前检查时写「检查条件」；指交付完成要求时写「验收条件」；指选择分支的条件时直接写完整问句。
- 不使用「落地、兜底、骨架、护栏、逃生舱、铁律、锚点、一等公民」等不能单独说明机制的表达。分别写明实施动作、默认或最终处理、接口或伪代码结构、范围检查、完整结果读取入口、必须满足的限制、对应位置、独立资源。
- 真实且必要的技术术语保留，例如状态机、前缀匹配、事件溯源、KV cache、fencing。首次出现时先用完整句子解释，再给出术语和英文原名；不得为了清理 AI 味而把准确术语改成模糊白话。
- 句子至少写清动作和对象；条件会改变结论时，还要写清条件与结果。标题不能只剩一个抽象名词。

## 13. AI 味检查

- 交付前逐句问「删掉它，读者会损失哪项事实、因果、边界或操作？」答不上来就删除。
- 「不是 X，而是 Y」「不仅 A，还 B」只在纠正读者很可能持有的具体误解时使用；同一文件出现三次，说明句式已经替代论证，必须改写。
- 不使用「方法提醒」「不做对会怎样」「可以直接检查的问题」等反复出现的元话语标签。直接写复核对象、故障后果或检查问题。
- 章节五段职责保持不变，但段首、列表数量、加粗标签和段落长度由内容决定，不要求形式对称。
- 不写「取决于场景」「各有优劣」后停止判断。先给默认选择，再写使默认选择失效的可观察条件。
- 「本书测量」「本书推算」「论文实测，未复现」必须和被限定的数字或结论写在同一句或紧邻的完整句中，不能单独成句，也不能只充当句首标签。读者应当一眼看出证据性质限定的是哪项内容。
- 「这、那、上面、下面」只能在前一句存在唯一指代对象时使用。附近同时出现多行、多版本、多包或多项指标时，直接写项目名、版本、路径、表号或指标名；不得写「那一行」「另一包」「那个数」。
- 不把编辑过程写进正文。删掉「引用时会分开标」「后文会展开」一类对未来排版或写作动作的说明；当场写明差异，交叉引用用「见第 N 章 §N.M」。
- 短句必须独立表达可判断的命题。禁止用「合起来有个名字」「剩下的就是本书要讲的东西」「这不是巧合」「就这些」制造节奏或悬念；改写时补出对象、依据和结论成立的范围。
- 隐喻或口语如果省略了机制，就改成实际动作。例如「切点被吸附」改为「向前查找最近的合法切点」，「日志没打通」改为「日志没有被采集或上报」。真实技术术语不在此列。
- 最高级、情绪判断和因果断言必须有比较范围或证据。不能证明因果时，写明观察到的差异及证据来源，不写「这不是巧合」「最重要的一条」。

## 14. 作者声音与人味

「人味」不是往技术文里加口头禅、笑话或无关经历，而是让读者看见一个具体作者如何取得证据、作出选择并承担判断。执行时遵守以下约束：

- 客观机制、数字和来源照常直接陈述；作者亲自完成的检索、测量、取舍、纠错和建议，可以用「我」。不要把「本书」机械替换成「我」，也不为提高第一人称频率而改句子。
- 「我」主要出现在四种位置：说明查了什么或没查到什么；说明复核为何改变结论；解释为何保留某项证据或安排章节；明确给出默认建议及其失效条件。
- 每个部分最多选择一两处真实的研究过程进入阅读主路径。优先保留会改变读者判断的错误、反例和选择理由；测量命令、完整检索过程仍放在「版本与复核」。
- 不虚构「我原本以为」「令我震惊」之类的心理活动。只有底稿、修订记录或实际取证过程能够支持时才写个人经历。
- 面向读者的「你」只用于具体决策或可观察场景，例如「你的仓库超过 1000 个文件」；不使用假亲密、反问串或替读者预设情绪。
- 段落节奏服从推理。证据复杂时允许长句展开，结论明确时可以短句收束；不得故意随机化句长、插入口语或制造语病来模仿人写作。
- 不为「人味」牺牲现有术语、证据等级和边界。作者声音负责说明谁在判断，不能把推断改写成事实。

本节不设第一人称数量、句长方差或段落长度阈值。可以被机械达成的表面指标，很容易制造新的 AI 味；复核问题只有两个：「这里是否存在需要作者承担的判断？」「读者是否知道这个判断为何作出？」

## 15. 正文不能写成工作笔记

研究底稿记录「查了什么、没查到什么、下一步怎么核对」；正式正文回答「读者因此知道什么、这会怎样改变判断」。两者不能直接混写。

- 删除纯编辑记录，例如「本节三处引用同出此文」「段落顺序有一处例外」「这是写作时给自己定的硬约束」。它们不改变读者对技术内容的判断。
- 调研限制不能用「诚实说明」「本书没能」「尚未做齐」作标签。直接写可确认的证据范围，以及超出该范围后不能得出什么结论。
- 不用「拆开说」「两个细节」「一条边界」「最后一件事」「含义 / 实操」充当提纲。需要列表时，先说明列表中的项目共同回答什么问题；只有一句时直接写完整句子。
- 「规则：X」只有在 X 已经写清对象、条件和动作时才可保留。否则改成因果句，例如「综述适合识别比较维度；协议当前状态必须以规范与仓库为准」。
- 表格和代码块前允许短引导句，但引导句必须说明读者为什么要看后面的材料，不能只写「见下」「对照如下」。
- 证据等级、未复现、资料缺失和适用边界不是笔记，必须保留；改写目标是让限制直接约束结论，而不是删除限制。

自查问题：**这句话是在记录作者的工作过程，还是在改变读者对结论的理解？** 前者移入 `.review/` 或「版本与复核」；后者改成完整的读者语言后留在正文。
